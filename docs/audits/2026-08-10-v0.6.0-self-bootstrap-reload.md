# v0.6.0 self-bootstrap reload test and audit

- Date: 2026-08-10
- Status: `completed_with_findings`
- Release under test: `0.6.0`
- Protocol: v5
- Environment: Windows x64, VS Code 1.132.0, local trusted folder workspace
- Tool surface: 26 bounded MCP tools
- Related procedure: [VS Code Agent Bridge 0.6.0 Windows x64 acceptance](../acceptance/v0.6.0-windows-x64.md)

## Scope

This run tested the bridge while it was being used to inspect and manage its own repository. It focused on the reload boundary after upgrading the Codex-managed MCP executable and tool allowlist from `0.5.1` to `0.6.0`.

The run verified:

- MCP and extension version alignment after restarting Codex;
- VS Code instance re-registration after **Developer: Reload Window**;
- workspace setup discovery and first-use onboarding;
- optimistic experiment-title protection;
- explicit checkpoint creation; and
- refusal to replace an existing active experiment.

The run did not apply source edits, save source documents, create a Git commit or start a second experiment.

## Method and preconditions

1. Configure Codex from the `0.6.0` extension and restart Codex.
2. Confirm the managed MCP executable is `0.6.0` and all 26 tools are loaded.
3. Reload the VS Code window and poll `vscode_list_instances` until the new extension host registers.
4. Inspect workspace onboarding and the active ordinary experiment.
5. Invoke `vscode_rename_experiment` with an intentionally stale `expectedTitle` while onboarding is unconfigured.
6. Complete the native onboarding prompt, then inspect workspace setup again.
7. Repeat the stale-title probe after onboarding.
8. Create one explicit recovery checkpoint with `vscode_create_experiment_checkpoint`.
9. Attempt to start a second ordinary experiment in the same window.

Machine-specific paths and identifiers are omitted from this report. The repository root is represented as `<REPOSITORY>`.

## Finding 1: interactive mutation completes after the caller times out

- ID: `AUDIT-2026-08-10-01`
- Severity: High
- Components: MCP RPC client, bridge socket lifecycle, workspace onboarding

### Expected

An interactive mutation should have one unambiguous terminal outcome. If the MCP call reports failure, the extension must not later commit the mutation unless the protocol explicitly reports a pending user action that can be reconciled.

### Observed

`vscode_rename_experiment` entered first-use workspace onboarding. The MCP call returned:

```text
TIMEOUT: Timed out while calling experiment/rename.
```

The user then confirmed the native VS Code prompt. Despite the reported timeout, the extension continued processing, enabled workspace experiments through the VS Code Configuration API and produced settings save/close checkpoints. A subsequent setup read reported `onboarding=enabled`.

The timeout layers are inconsistent:

- `DEFAULT_BRIDGE_TIMEOUT_MS` is 5 seconds;
- accepted bridge sockets are destroyed after 10 seconds of inactivity; and
- the Codex MCP tool timeout is 120 seconds, which cannot extend either inner timeout.

Relevant code:

- [`packages/protocol/src/constants.ts`](../../packages/protocol/src/constants.ts) defines the 5-second default;
- [`packages/mcp-server/src/rpc-client.ts`](../../packages/mcp-server/src/rpc-client.ts) rejects and forgets the pending request when that timeout elapses;
- [`packages/vscode-extension/src/bridge-host.ts`](../../packages/vscode-extension/src/bridge-host.ts) applies the socket timeout; and
- [`packages/vscode-extension/src/workspace-onboarding.ts`](../../packages/vscode-extension/src/workspace-onboarding.ts) continues awaiting the modal choice and writes settings after confirmation.

### Impact

- The Agent may retry an operation that actually succeeded.
- Retries can duplicate checkpoints or conflict with later state.
- The activity and audit trail disagree with the result returned to the caller.
- Increasing only Codex's outer tool timeout does not resolve the inconsistency.

### Recommendation

Use an explicit asynchronous user-action protocol: return a stable `USER_ACTION_REQUIRED` or pending operation identifier, let the UI complete independently, and provide a bounded status/reconciliation call. Alternatively, propagate cancellation and idempotency through the bridge so a timed-out caller cannot leave an untracked mutation running. A longer per-method timeout may improve usability but is not sufficient by itself.

### Closure criteria

1. An onboarding request never reports failure before a later successful settings mutation.
2. Retrying the same logical operation is idempotent or rejected with a stable reconciled result.
3. Automated coverage holds the modal open beyond the ordinary RPC timeout and verifies that client and extension outcomes still agree.

## Finding 2: the bridge is invisible during experiment recovery

- ID: `AUDIT-2026-08-10-02`
- Severity: Medium
- Components: extension activation, experiment storage initialization, local instance registry

### Expected

After Reload Window, clients should either discover the new instance promptly with an explicit `initializing` state or receive a stable error that distinguishes recovery from a disabled, crashed or missing extension.

### Observed

Immediately after Reload Window, the previous instance was correctly removed, but repeated `vscode_list_instances` calls returned zero instances. The new extension host was running and activation had begun. The bridge descriptor was created at `01:56:43Z` and did not become discoverable until approximately `01:57:22Z`, a gap of about 39 seconds.

The active experiment journal was approximately 61 MB, contained roughly 1,515 captured documents and had `partial` health. Extension activation currently awaits experiment initialization before calling `host.start()`:

- [`packages/vscode-extension/src/extension.ts`](../../packages/vscode-extension/src/extension.ts) awaits `experiments.initialize()` before registering the host.

The journal size is relevant context, but this run did not isolate storage size as the sole cause of the delay.

### Impact

- Clients can falsely conclude that no compatible VS Code instance exists.
- Reload automation is race-prone and requires arbitrary polling delays.
- A slow recovery is indistinguishable from extension activation failure.
- No Bridge diagnostic can be called during the interval because the instance is absent from discovery.

### Recommendation

Publish a minimal instance descriptor before long-running recovery and expose an explicit lifecycle such as `initializing`, `ready` or `degraded`. State-dependent calls should return a stable `BRIDGE_INITIALIZING` response until recovery completes. If early registration is incompatible with current handlers, add a separate lightweight readiness record rather than presenting an empty registry.

### Closure criteria

1. A reloaded window becomes discoverable within a small bounded interval independent of journal size, or advertises `initializing` immediately.
2. Clients can distinguish initializing, unavailable and incompatible instances without reading logs.
3. An integration test seeds a large/partial experiment store, reloads the extension host and verifies the complete discovery-to-ready transition.

## Side effects and artifacts

- Native user confirmation enabled `vscodeAgentBridge.experiments.enabled` in workspace-folder settings.
- The onboarding flow generated settings save/close checkpoints after the MCP timeout.
- The audit intentionally created one explicit checkpoint, sequence 307.
- The active experiment title remained `自举开发`.
- No source document was modified by the audit.
- No Git commit, branch, push or pull request was created.

## Overall assessment and next gate

The `0.6.0` self-bootstrap path is functionally usable after version alignment and onboarding. The tool surface, stale-title guard, explicit checkpoint path and active-session guard all behaved as designed.

The run is not clean enough to close as passed because Finding 1 allows a state-changing operation to succeed after the caller received a failure. Finding 2 is a reliability and diagnosability gap at every reload boundary. Both findings should receive regression tests before the next self-bootstrap audit. The follow-up report must be a new dated file in this directory and must link back to this report rather than rewriting its status.
