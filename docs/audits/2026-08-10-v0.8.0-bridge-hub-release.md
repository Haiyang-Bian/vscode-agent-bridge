- Date: 2026-08-10
- Status: `completed_with_findings`
- Scope: protocol v7, 44-tool catalog, local usage insights, native Bridge Hub, source and packaged Extension Host regression
- Environment: Windows x64, Bun 1.3.11, VS Code test runtime 1.132.0

## Method and preconditions

The audit ran from `codex/bridge-hub-v0.8` after fast-forwarding the merged v0.7 baseline. Existing `.idea`, `.codex` and workspace settings remained outside every feature commit. Tests used isolated temporary registry, workspace, profile and managed-worktree roots.

Executed gates:

1. repeated `bun run check` after each milestone;
2. `bun run test:e2e` against a real Extension Development Host;
3. `bun run build:mcp:exe`, `package:vsix`, `package:test-bundle`, `test:artifact` and `release:checksums`;
4. packaged VSIX installation into an isolated profile and the full v0.7 longitudinal regression;
5. VSIX inventory and release-script privacy/surface audit.

## Findings

### 1. E2E completion marker duplicated protocol constants

- Severity: low
- Evidence: the first source Extension Host run completed with `2 passing`, but the outer script rejected the correct v7/44 marker because it still compared literal v6/42 values.
- Impact: false-negative release gate; no runtime Bridge failure.
- Resolution: both source and packaged E2E scripts now derive protocol version and tool count from the protocol package. The full source and packaged suites passed afterward.

### 2. VS Code test runtime emits upstream deprecation/noise warnings

- Severity: informational
- Evidence: the runner emitted Node `DEP0169`/`DEP0190`, Mermaid proposed-API and Agent Host channel warnings while all Bridge tests passed.
- Impact: noisy CI output only; no warning originated from a Bridge API surface or affected assertions.
- Recommendation: track upstream test-cli/VS Code runtime updates separately; do not suppress warnings in a way that hides Bridge failures.
