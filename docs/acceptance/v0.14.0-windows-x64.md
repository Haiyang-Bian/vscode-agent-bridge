# v0.14.0 Windows x64 acceptance

This is an unpublished protocol-v12 candidate. Keep earlier acceptance records unchanged. Use a disposable trusted workspace and a fresh VS Code Profile; never collect bearer credentials, IPC endpoints, raw Codex configuration, source snapshots or terminal/debug content.

## Installation and service

1. Verify the supplied hashes, install the 0.14.0 VSIX over the earlier version and run **Configure Codex**. Confirm the managed block uses authenticated HTTP and exposes exactly 57 tools.
2. Run Doctor. Confirm one healthy 0.14.0 daemon, RPC v12, a valid current-user login task and the current VSIX release. No VS Code window is a healthy daemon state.
3. Run 20 concurrent starts against an isolated service identity. Confirm one daemon wins and every duplicate authenticates the existing owner or fails closed.
4. Exercise identical reinstall, successful upgrade, failed-candidate rollback, restart, configuration conflict and uninstall in an isolated service/config/registry. After a successful upgrade, confirm only the active executable and one verified rollback directory remain; transaction/task references survive cleanup and cleanup failure does not stop the daemon.
5. Inspect current-user/SYSTEM ACLs. A denied-access test under another Windows identity remains a separate requirement before cross-user claims.

## Direct Bridge and compatibility

1. Open the disposable fixture with 0.14.0 and keep a v11 window available if possible. `vscode_list_instances` must report the v12 window as compatible and the v11 descriptor as incompatible. `releaseAlignment` must separately identify current/older/newer/unknown releases.
2. From two MCP clients, read an unsaved buffer through the same daemon PID. Cancel or delete one session and confirm the other remains usable.
3. Saturate one session: the ninth active request must promptly receive JSON-RPC `-32002` with its original ID and `SERVER_CAPACITY_REACHED`; the first eight finish and the session remains usable. Repeat at global capacity across clients.
4. Without creating an experiment, prepare/apply a text change in the disposable fixture, save, format, apply the fixture Code Action, update workspace configuration, and prepare/apply a resource change. Verify trust, forged-root, stale-version/hash and cancelled-call rejection.
5. Exercise prepared/persisted Task and Debug definitions. Confirm handle TTL, instance/root binding, one-use and fingerprint/provenance checks. External effects are not reported as recoverable.

## UI and legacy data

1. Confirm the Activity Bar contains exactly **Status** and **Agent Activity**.
2. Run an Agent mutation while another editor is focused. The active editor must not change. Select the resulting activity item and only then confirm VS Code reveals the target.
3. Confirm ordinary reads do not add activity entries; mutations, running Task/Debug work and failures do.
4. Seed disposable legacy Bridge experiment metadata. Confirm 0.14.0 reports but never loads it. Open its location, cancel deletion once, then confirm deletion removes only Bridge-owned metadata/snapshots and leaves Git branches/worktrees untouched.
5. When stable APIs do not expose Profile identity or an output source, confirm Status says the API does not provide it rather than reporting extension failure.

## Evidence

Record the commit, version, EXE/VSIX hashes, actual tool count, selected calls, shared PID, version directories and any remaining v11 window in a new dated report under `docs/audits`. A local pass does not establish Marketplace readiness, a formal release or cross-machine/cross-user acceptance.
